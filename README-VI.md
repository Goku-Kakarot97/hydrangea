# Hydrangea

Framework mạng non-blocking nhỏ gọn trên Java NIO (Java 21, không phụ thuộc thư viện ngoài). Xem `REVIEW.md` để biết lý do thiết kế so với XNIO.

```java
try (var group = new EventLoopGroup()) {
    Server.bind(group, new InetSocketAddress(7000), Options.defaults(), () -> new Handler() {
        public void onRead(Connection c, ByteBuffer data) {
            c.write(ByteBuffer.allocate(data.remaining()).put(data).flip()); // data chỉ hợp lệ trong lời gọi này
        }
    });
    Thread.currentThread().join();
}
```

## Cấu trúc module

Một repo, nhiều module Maven. Lõi dùng chung, mỗi giao thức là một module riêng chỉ phụ thuộc vào những gì nó cần. Tên gói giữ nguyên `io.hydrangea.*`.

| Module | Chứa | Phụ thuộc |
|---|---|---|
| `hydrangea-core` | `EventLoop`, `Connection`, `Server`, `Client`, `UdpSocket`, `BufferPool`, `codec`, `pipeline`, `tls`; test helper dùng chung (`TestTls`, `Fuzz`) qua test-jar | (không có) |
| `hydrangea-quic` | QUIC v1 (thử nghiệm) | core |
| `hydrangea-http` | HTTP/1.1, HTTP/2 (HPACK), HTTP/3 server và client; WebSocket; Server-Sent Events | core, quic |
| `hydrangea-grpc` | gRPC server và client | core, http |
| `hydrangea-amqp` | client AMQP 0-9-1 (RabbitMQ) | core |
| `hydrangea-mqtt` | client MQTT 3.1.1 và 5.0, gồm cả MQTT qua WebSocket | core, http |
| `hydrangea-redis` | client Redis (RESP2/RESP3, pipeline tự động, pub/sub, transaction, script) | core |
| `hydrangea-postgres` | client PostgreSQL (giao thức v3, pipeline tự động, cache prepared statement, SCRAM-SHA-256, pool nhỏ) | core |
| `hydrangea-mysql` | client MySQL (giao thức MySQL, pipeline lệnh, prepared statement phía server với giao thức binary, `caching_sha2_password`, TLS, pool nhỏ) | core |
| `hydrangea-sql` | giao diện chung của hai client SQL (`SqlPool`, `SqlClient`, `SqlResult`, `SqlRow`, `SqlException`): code viết một lần chạy trên PostgreSQL hoặc MySQL | - |
| `hydrangea-kafka` | client Kafka (producer có idempotent, consumer group, SASL/PLAIN) | core |
| `hydrangea-micrometer` | `MetricsSink` cho Micrometer (Prometheus, OTLP, Datadog, JMX...). Module duy nhất có phụ thuộc ngoài (`micrometer-core`) | core |
| `hydrangea-examples` | ví dụ chạy được (`io.hydrangea.examples`); test chạy xuyên module và `ArchitectureTest`; bước build cuối gộp class của mọi module vào `target/classes` ở gốc | tất cả (không xuất bản) |

Không module thư viện nào có phụ thuộc ngoài (chỉ JDK); chỉ test và benchmark dùng thêm thư viện (JUnit...). `hydrangea-examples` có `ArchitectureTest`: kiểm tra gói nào được dùng gói nào (core không được biết giao thức), và rằng mã chính chỉ import JDK.
Thêm một giao thức mới (Redis, Kafka...) là thêm một module chỉ phụ thuộc `hydrangea-core`: `hydrangea-amqp` là mẫu nhỏ nhất, và `ArchitectureTest` buộc bạn khai báo gói mới được dùng gì.

```
mvn test                              # tất cả
mvn -pl hydrangea-amqp -am test       # một module và những gì nó cần
mvn -pl hydrangea-http -am test
```
`mvn compile` (hoặc `test`) vẫn gom class vào `target/classes` ở gốc, nên mọi lệnh `java -cp target/classes ...` bên dưới và các script trong `benchmark/`, `interop/`, `h2spec/`, `autobahn/`, `k8s/` chạy như trước.

## Khái niệm
- **EventLoop**: 1 thread + Selector + task queue + timer. Mọi thao tác trên kênh chạy ở đây → không cần lock. Tự xây lại Selector khi gặp lỗi spin (epoll) của JDK.
- **EventLoopGroup**: N loop, chia kết nối round-robin; `metrics()` trả số liệu toàn nhóm.
- **Connection**: `write` (thread-safe, có callback khi gửi xong/bị huỷ), `close`, `closeAfterFlush`, `setAutoRead`, `isWritable`.
- **Handler**: `onActive / onRead / onWritabilityChanged / onClose`. Một instance mỗi kết nối.
- **Pipeline + Stage**: nối nhiều bước xử lý; inbound 0→n-1, outbound n-1→0.
  `LineStage`, `LengthPrefixStage`, `TlsStage`, hoặc tự viết `Stage`.
- **TLS**: `TlsStage.server(ctx)` / `TlsStage.client(ctx, host, port)` (có kiểm tra hostname). Stage phía sau chỉ nhận `onActive` sau khi handshake xong.
- **UdpSocket**: gửi/nhận datagram không chặn; quá tải thì *drop có đếm* thay vì phình bộ nhớ.
- **BufferPool**: pool theo cỡ 2^n (256B–1MiB), dùng với `write(buf, () -> pool.release(buf))`.
- **Metrics**: kết nối mở/đóng/đang hoạt động, byte đọc/ghi, task, số lần rebuild selector, datagram, `maxBlockNanos` (độ trễ loop). Core chỉ định nghĩa interface `MetricsSink`; muốn đẩy sang Micrometer thì thêm `hydrangea-micrometer` rồi `group.metrics().bindTo(new MicrometerSink(registry))` (đọc lúc scrape, loop không tốn thêm gì; tên như `hydrangea.connections.opened`, `hydrangea.http.responses{class=2xx}`). Viết sink cho OpenTelemetry hay thư viện khác chỉ cần cài đặt 4 phương thức. **Độ trễ** đo bằng `Latency` của core (histogram logarit, 8 bước mỗi lần gấp đôi, sai số tối đa 12,5%): đường chạy chính chỉ đọc đồng hồ và cộng một ô đếm đã cấp sẵn (không cấp phát, không khoá, không queue), còn một thread nền `hydrangea-metrics` mỗi 5 giây gộp các ô và tính p50/p90/p99/p99,9/max **của cửa sổ đó** (không phải của cả đời process); khi chưa gắn sink nào thì ghi độ trễ chỉ là một lần đọc biến volatile. Đã đo: HTTP/1.1 và HTTP/2 server (`http.server.duration`, từ lúc parse xong header đến lúc có response) và Redis client (`redis.commands{outcome=ok|error|failed}`, `redis.command.duration`, `redis.commands.pending`, `redis.connections.lost`, `redis.reconnects`). Chưa đo: HTTP/3, in-flight của server, gRPC/WebSocket/SSE, và các client còn lại (Kafka, MQTT, AMQP, HttpClient). Mỗi meter mới tạo bằng `metrics.counter(...)`, `metrics.gauge(...)`, `metrics.latency(...)` (cùng tên và tag thì dùng chung một cái).
  Đã đo (đều đọc lúc scrape; độ trễ chỉ ghi khi đã gắn sink, và đo theo batch hoặc dùng mốc thời gian sẵn có để khỏi tốn đồng hồ):
  - **HTTP server** (1.1, 2, 3): `http.requests`, `http.responses{class}`, `http.timeouts`, `http.server.active` (request đang xử lý), `http.server.duration`, `http2.resets{by=peer}`.
  - **HttpClient**: `http.client.requests{class=2xx..5xx|error}`, `http.client.active`, `http.client.duration`, `http.client.retries`, `http.client.redirects`.
  - **WebSocket** (`side=client|server`): `websocket.connections`, `websocket.messages{direction}`, `websocket.bytes{direction}`, `websocket.closes{code}`. **SSE**: `sse.connections`, `sse.events{side,direction}`, `sse.slow.disconnects`, `sse.reconnects`.
  - **gRPC** (opt-in: `GrpcMetrics.server(metrics)` / `GrpcMetrics.client(metrics)` làm interceptor): `grpc.{server,client}.calls{method,code}`, `.active`, `.messages{direction}`, `.duration`.
  - **TLS**: `tls.handshakes{result=ok|failed, protocol}`, `tls.handshake.duration`.
  - **PostgreSQL**: `pg.queries{outcome=ok|error|failed|timeout}`, `pg.query.duration`, `pg.queries.pending`, `pg.connections.lost`, `pg.cancels`, `pg.statements.replanned`, `pg.binary.parameters`, `pg.binary.columns`, `pg.reconnects`. Pool: `pg.pool.waiting` (caller đang chờ kết nối), `pg.pool.acquire.duration` (chờ bao lâu, chỉ tính người đã chờ), `pg.pool.acquire.timeouts`, `pg.pool.connections.replaced{reason=broken|lifetime}`, `pg.pool.pings.failed`.
  - **MySQL**: cùng bộ với tiền tố `my.`: `my.queries{outcome=ok|error|failed|timeout}`, `my.query.duration`, `my.queries.pending`, `my.connections.lost`, `my.reconnects`, `my.kills` (`KILL QUERY` đã gửi), và `my.pool.*` như trên.
  - **Redis**: `redis.commands{outcome}`, `redis.command.duration`, `redis.commands.pending`, `redis.connections.lost`, `redis.reconnects`.
  - **Kafka producer**: `kafka.producer.records{outcome}`, `.bytes`, `.retries`, `.rejected{reason}`, `.batch.duration` (tuổi của batch lúc được ack, gồm cả linger). **Consumer**: `kafka.consumer.records`, `.bytes`, `.fetches`, `.fetch.errors`, `.lag` (tổng các partition đang giữ), `.rebalances`, `.rebalance.duration`, `.commits{outcome}`, `.heartbeat.failures`.
  - **MQTT client**: `mqtt.client.messages{direction,qos}`, `.publish.duration` (đến lúc broker ack), `.publish.failures`, `.pending`, `.connections.lost`, `.reconnects`. **AMQP**: `amqp.messages{direction}`, `amqp.confirms{result}`, `amqp.confirm.duration`, `amqp.unconfirmed`, `amqp.acks{type}`, `amqp.returned`, `amqp.publish.failures`, `amqp.connections.lost`.
  - Chưa đo: kích thước request/response, theo route, MQTT/AMQP server, QUIC, từng loop riêng, bộ nhớ (`BufferPool`, direct buffer), pool kết nối của HttpClient, DNS/connect/TLS riêng của từng request.
- **HTTP/1.1** (`io.hydrangea.http`): `HttpServer.bind(group, addr, handler)` hoặc thêm `HttpServerStage` vào pipeline (sau `TlsStage` cho HTTPS).
  Keep-alive, pipelining đúng thứ tự, body `Content-Length` và chunked, `Expect: 100-continue`, HEAD, handler bất đồng bộ (`CompletionStage`).
  Parser chặt để chống request smuggling (CL+TE, CL xung đột, LF trần, obs-fold, khoảng trắng trước dấu `:`) và có giới hạn header/body (431/413).
- **HttpRouter** (`io.hydrangea.http`): định tuyến theo method + mẫu đường dẫn, là một `HttpHandler` nên cắm thẳng vào `HttpServer.bind`.
  Path variable `/users/{id}`, catch-all `/files/{path...}`, request param (query string + form body, tham số lặp `?tag=a&tag=b`)
  với getter có kiểu (`pathInt`, `paramInt`, `paramBool`, `requiredParam`... sai kiểu hoặc thiếu → 400).
  Mẫu cụ thể hơn thắng (`/users/me` > `/users/{id}`), 405 kèm `Allow`, `throw new HttpStatusException(404, "...")`, route bất đồng bộ (`getAsync`).
- **HttpClient** (`io.hydrangea.http`): client HTTP/1.1 bất đồng bộ (`send(ClientRequest)` → `CompletableFuture<ClientResponse>`).
  Pool keep-alive theo host (giới hạn kết nối, hàng đợi chờ), HTTPS có kiểm tra hostname, timeout (connect / tổng / không hoạt động),
  huỷ future là đóng kết nối, tự retry 1 lần với GET/HEAD/PUT/DELETE khi kết nối cũ đã chết (POST không bao giờ retry),
  theo redirect (không bao giờ hạ từ https xuống http, bỏ `Authorization`/`Cookie` khi đổi origin), parser response chặt và có giới hạn kích thước.
  **HTTP/2 client** (`HttpClientConfig.withHttp2(Http2ClientConfig.defaults())`): TLS thương lượng `h2` qua ALPN và quay về HTTP/1.1 nếu server không có; `http://` chỉ dùng HTTP/2 khi bật
  `cleartextPriorKnowledge`. Mọi request tới một host dùng chung một kết nối (loạt request đầu tiên chờ kết quả ALPN của kết nối đầu thay vì mở mỗi cái một kết nối), tôn trọng giới hạn stream
  của server và flow control hai tầng cả chiều gửi lẫn nhận. Cùng API với HTTP/1.1: `send`, `stream` (có `pause`/`resume`/`cancel`), upload `RequestBody`/`BodySink` có backpressure, `Expect: 100-continue`,
  redirect, timeout từng request (hủy chỉ reset stream đó, không đụng kết nối). GOAWAY/REFUSED_STREAM chứng minh được là chưa xử lý nên **được gửi lại an toàn kể cả POST** (khác HTTP/1.1).
  Kiểm chứng: 17 test với server giả viết frame thô (GOAWAY, cửa sổ nhỏ, header sai, PUSH_PROMISE...), 16 test với server Hydrangea, và Node `http2` làm server độc lập (`interop/run.sh`).
  **Giải nén gzip/deflate** (`withDecompression(true)`, mặc định tắt): tự gửi `Accept-Encoding: gzip, deflate` (trừ khi request tự đặt) và giải mã theo luồng, cả bản đệm lẫn `stream` (pause vẫn đúng khi một khúc nén nở thành nhiều khúc);
  `maxResponseBytes` giới hạn kích thước **sau khi giải nén** nên chặn được bom giải nén; gzip nhiều member, kiểm CRC32/độ dài, deflate dạng zlib lẫn raw. Response không còn `Content-Encoding`/`Content-Length`.
  **Cookie** (`withCookieJar(new InMemoryCookieJar())`, RFC 6265): `Set-Cookie` từ mọi response kể cả từng bước redirect, `Max-Age` thắng `Expires`, domain/path match, host-only, `Secure` chỉ qua https và không bị ghi đè từ http, giới hạn 4096 byte/cookie, 50/domain, 3000 tổng.
  **Lưu ý bảo mật:** danh sách public suffix tích hợp **không đầy đủ** (không có Public Suffix List); cắm vào `new InMemoryCookieJar(predicate)` danh sách thật nếu cookie quan trọng. `SameSite` chỉ lưu, không áp dụng.
  **Proxy HTTP** (`withProxy(ProxyConfig)`, hoặc `ProxyConfig.fromEnvironment()` đọc `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`): `http://` gửi dạng absolute-form, `https://` (và h2c prior knowledge) qua `CONNECT` nên TLS và kiểm chứng chứng chỉ là với origin chứ không phải proxy;
  tên origin không được phân giải ở máy mình; `Proxy-Authorization: Basic` gửi sẵn và không bao giờ tới origin; proxy từ chối (407, 403...) báo lỗi nêu rõ câu trả lời của proxy; `noProxy` chấp nhận `*`, `example.com`, `.example.com`, `*.example.com`, IP.
  Chưa có: SOCKS, TLS tới proxy, WebSocket client qua proxy, CIDR trong `noProxy`.
  **h2c upgrade** (`Http2ClientConfig.withCleartextUpgrade(true)`, mặc định tắt): request đầu của kết nối `http://` mang `Upgrade: h2c`; server trả 101 thì kết nối thành HTTP/2 và request đó là stream 1, ngược lại tiếp tục HTTP/1.1.
  Chỉ request có body trong bộ nhớ mới đưa ra đề nghị. RFC 9113 đã bỏ cơ chế này và nhiều server (nginx, Envoy, Node.js) không hỗ trợ.
  Chưa có: pipelining.
- **HTTP/2 server** (RFC 9113, RFC 7541; `Http2Config`): bật bằng `HttpConfig.defaults().withHttp2(Http2Config.defaults())`. Cùng một cổng phục vụ cả HTTP/1.1:
  cleartext nhận ra HTTP/2 qua "client preface" (prior knowledge), TLS qua ALPN `h2` (`TlsStage.server(ctx, List.of("h2", "http/1.1"))` do `HttpServer.bind` tự làm).
  Dùng lại đúng `HttpHandler`/`HttpRouter` như HTTP/1.1 (`request.version()` là `"HTTP/2"`). HPACK tự viết (bảng tĩnh/động, Huffman; đối chiếu ngẫu nhiên với Netty hai chiều, 67 nghìn header),
  multiplexing, flow control theo stream và theo kết nối (cả chiều nhận lẫn chiều gửi, gửi luân phiên giữa các stream, dừng khi kết nối bị đầy), GOAWAY khi tắt êm, `Expect: 100-continue`.
  Chặn tấn công: giới hạn stream đồng thời (REFUSED_STREAM), rapid reset, flood PING/SETTINGS/PRIORITY/DATA rỗng (ENHANCE_YOUR_CALM), CONTINUATION flood, bom HPACK,
  header list quá lớn (431), request sai chuẩn (tên viết hoa, header riêng của kết nối, `Content-Length` lệch body...) bị RST_STREAM.
  Kiểm thử: 23 test frame-level + JDK `HttpClient` qua TLS, kiểm bằng đột biến (8/8 bị bắt), và **h2spec 147 test**: TLS 147/147, cleartext 146/147 (`h2spec/run.sh`; test còn lại không thể qua
  trên cổng dùng chung với HTTP/1.1 vì byte rác được coi là request HTTP/1.1).
  **SSE và WebSocket chạy trên stream HTTP/2**: `Connection` là một interface (socket hoặc một stream), nên `SseResponse` và `WebSocketUpgrade` chạy nguyên vẹn trên stream
  (WebSocket theo RFC 8441: `CONNECT` + `:protocol`, server quảng bá `SETTINGS_ENABLE_CONNECT_PROTOCOL`; router vẫn thấy một `GET`). Tắt êm (`shutdownGracefully`) yêu cầu các stream dài tự kết thúc.
  **Request body dạng stream** (`wantsStreamingBody`/`handleStreaming`, `postStream` của router): cửa sổ flow control của stream chính là backpressure, `pause()` giữ lại credit và dữ liệu đang bay.
  Kiểm chứng độc lập: curl (SSE, upload 60 MB), client `http2` của Node (WebSocket RFC 8441), JDK `HttpClient`, h2spec (`interop/run-server.sh`).
  **h2c upgrade phía server**: request HTTP/1.1 có `Upgrade: h2c` + `HTTP2-Settings` hợp lệ được trả 101 rồi chạy tiếp HTTP/2 (request đó là stream 1, settings trong header được áp dụng) - đây là cách `curl --http2 http://...` và JDK `HttpClient` mở HTTP/2 trên cleartext.
  Không bao giờ nâng cấp qua TLS (RFC 7540 §3.2); `HTTP2-Settings` hỏng thì request được phục vụ như HTTP/1.1 bình thường.
  **Server push** (`HttpResponse.push("/style.css")`, RFC 9113 §8.4): `PUSH_PROMISE` gửi trước response, request giả định chạy qua chính handler (mang theo `accept-encoding`, `accept-language`, `user-agent`, `cookie` của request gốc, hoặc header route tự chọn),
  tôn trọng `ENABLE_PUSH` và `MAX_CONCURRENT_STREAMS` của client, mỗi đường dẫn chỉ hứa một lần trên mỗi kết nối, tối đa 16 mỗi response, không đẩy khi response lỗi, stream đẩy có cửa sổ flow control riêng và client hủy được bằng RST_STREAM.
  **Lưu ý:** server push đã bị bỏ trong thực tế (Chrome gỡ hỗ trợ năm 2022, các trình duyệt khác tắt); tính năng này còn dùng được với client không phải trình duyệt (như JDK `HttpClient`).
  **Response 101 qua HTTP/2 không tồn tại**: RFC 9113 §8.6 cấm mã 101 trong HTTP/2, nên server trả 501 cho nó là đúng chuẩn. Chuyển giao thức trên HTTP/2 dùng extended CONNECT (RFC 8441), cái đã dùng cho WebSocket ở trên.
  Chưa có: ưu tiên stream (đã bị RFC 9113 bỏ). HTTP/2 mặc định **tắt** (bật bằng `withHttp2`) vì bật ALPN đổi hành vi của HTTPS.
- **WebSocket** (`io.hydrangea.websocket`, RFC 6455): server là một route bình thường
  `router.get("/chat", r -> WebSocketUpgrade.accept(r.request(), config, () -> new MyListener()))`; client `WebSocketClient.connect(group, "wss://...", listener)`.
  Text/binary, phân mảnh, ping/pong tự động, đóng kết nối đúng thủ tục (mã + lý do, timeout), TLS (`wss`), subprotocol,
  keep-alive (`pingInterval`), giới hạn kích thước message, kiểm tra Origin mặc định (chống cross-site WebSocket hijacking).
  Parser chặt: RSV, opcode, mask, độ dài tối giản, UTF-8, mã đóng hợp lệ — vi phạm bị đóng với mã 1002/1007/1009 đúng RFC.
  **Streaming**: listener trả `streaming() == true` để nhận message theo từng mảnh (`onTextPart/onBinaryPart(part, last)`) thay vì gom hết — không bị `maxMessageBytes`
  chặn, ký tự UTF-8 không bao giờ bị cắt đôi giữa hai mảnh, sai UTF-8 đóng kết nối ngay tại byte hỏng. `ws.setAutoRead(false)` thật sự giữ lại cả dữ liệu đã đọc.
  Gửi: `sendTextPart/sendBinaryPart(part, last)` tạo fragment thật (ping/close chen giữa được), `sendBinaryStream(InputStream)` đọc 64 KiB một lần và chờ `whenWritable()`.
  **Nén `permessage-deflate`** (RFC 7692), mặc định tắt: `WebSocketConfig.defaults().withCompression(PerMessageDeflate.defaults())` cho cả server lẫn client.
  Thương lượng đủ tham số (`*_no_context_takeover`), giải nén theo luồng và dừng được giữa chừng, giới hạn kích thước **sau khi giải nén** (chống bom nén),
  không nén message nhỏ hơn `thresholdBytes`. Offer đòi `server_max_window_bits < 15` bị từ chối (JDK `Deflater` luôn dùng cửa sổ 32 KB) — kết nối vẫn chạy, chỉ không nén.
  Đóng kết nối sau lỗi giao thức dùng *lingering close* (FIN rồi xả nốt dữ liệu peer còn gửi) để frame Close không bị RST nuốt mất.
  Chưa có: các extension khác.
- **Server-Sent Events** (`io.hydrangea.sse`): `router.get("/events", r -> SseResponse.accept(r.request(), () -> new SseListener() {...}))`,
  rồi `emitter.send(SseEvent.data("...").event("price").id("7"))` từ bất kỳ thread nào (giữ thứ tự theo thread).
  Có heartbeat, đọc `Last-Event-ID` khi client kết nối lại, gợi ý `retry`, và tự ngắt client đọc quá chậm
  (`maxPendingBytes`) thay vì giữ bộ nhớ vô hạn. Dữ liệu nhiều dòng được tách thành các field `data:` nên không thể chèn field giả;
  `event`/`id` có xuống dòng bị từ chối. HTTP/1.1 dùng chunked, HTTP/1.0 dùng thân đóng khi kết thúc.
- **HTTP client streaming** (`HttpClient.stream(request, BodyListener)`): nhận response *khi nó đến* (`onHead`, `onData` từng đoạn, `onComplete`/`onError`),
  không giới hạn kích thước body nên dùng được cho tải file lớn và luồng vô tận. Có backpressure thật (`BodyControl.pause()` dừng đọc socket nên TCP làm chậm server),
  `StreamHandle.cancel()`, redirect được theo trước khi listener thấy gì, timeout request chỉ tính tới khi có header (sau đó là idle timeout), retry khi kết nối cũ chết.
- **SSE client** (`SseClient.subscribe(http, url, listener)`): giống `EventSource` của trình duyệt theo chuẩn WHATWG — parser tăng dần, `Last-Event-ID` khi kết nối lại,
  tôn trọng `retry:` của server, backoff lũy thừa khi lỗi liên tiếp, 204 = dừng hẳn, 404/sai content-type = lỗi cuối cùng không retry.
- **Upload dạng stream** (không nạp cả body vào bộ nhớ):
  *Client*: `ClientRequest.put(url).body(RequestBody.file(path))` (hoặc `RequestBody.stream(...)`, `RequestBody.producer(...)`; độ dài chưa biết → tự dùng chunked).
  Backpressure thật: producer chờ `sink.whenWritable()` nên bộ nhớ chỉ là một buffer 64 KiB dù file bao lớn. `.expectContinue()` đợi go-ahead của server (một lời từ chối như 401/413 không tốn byte body nào).
  Body "phát lại được" mới được retry/theo redirect 307-308; `streamOnce` thì không. Timeout request tính cả thời gian upload, nên đặt đủ lớn cho file lớn.
  *Server*: `router.postStream("/up", (req, body) -> { body.listen(listener); return future; })` nhận body từng đoạn, không bị giới hạn `maxBodyBytes`;
  trả lời sớm (vd 413) khi client còn đang gửi thì server vẫn xả có giới hạn (8 MiB / 5 giây) rồi mới đóng, để client không mất response vì RST.
  Lưu ý: khi một body bị `pause()`, server không biết client đã ngắt — hãy cấu hình `idleTimeout`.
- **Vận hành & chống lạm dụng**:
  *Tắt êm* `server.shutdownGracefully(timeout)`: đóng cổng ngay, kết nối keep-alive rảnh đóng ngay, request đang chạy được trả lời với `Connection: close`,
  WebSocket nhận Close 1001, SSE kết thúc (EventSource tự kết nối lại), upload đang dở được hoàn tất; hết `timeout` thì đóng cưỡng bức. `Handler.onDrain` cho handler thô.
  *Timeout HTTP* (`HttpConfig`): `headerTimeout` (mặc định 10 s, tính tổng từ byte đầu tiên — bị nhỏ giọt từng byte cũng không kéo dài được, chặn slowloris, trả `408`),
  `bodyTimeout` (30 s, body gom bộ nhớ), `keepAliveTimeout` (60 s). Không áp dụng khi app đang xử lý, hay khi đã chuyển sang stream/WebSocket/SSE. TLS có `handshakeTimeout` (10 s).
  *Giới hạn* (`Options`): `withMaxConnections(n)`, `withMaxConnectionsPerAddress(n)` — vượt ngưỡng thì đóng ngay và đếm vào `connectionsRejected`.
  *Quan sát*: `HttpConfig.withAccessLog(AccessLog.toLogger("access"))` (hoặc callback riêng), `metrics().snapshot().toPrometheus("hydrangea")` cho route `/metrics`.
  (Lưu ý: nếu backend log là `java.util.logging`, hook tắt của JDK có thể nuốt log của request kết thúc đúng lúc tắt êm; dùng Logback/Log4j2 hoặc `AccessLog` tự viết.)
  Đóng kết nối sau từ chối dùng *lingering close* để phản hồi lỗi không bị RST nuốt mất.
- **gRPC** (`io.hydrangea.grpc`, không phụ thuộc thư viện ngoài, chạy trên HTTP/2): đủ bốn kiểu gọi (unary, server/client/bidi streaming), `Status` với 17 mã,
  metadata (kể cả `-bin`), trailer, deadline (`grpc-timeout`, server huỷ handler khi quá hạn), huỷ call (RST_STREAM tới tận handler), nén gzip, giới hạn kích thước message
  (mặc định 4 MiB, chặn ngay từ 5 byte đầu), `HealthService` (`grpc.health.v1` Check/Watch). Message là byte: tự viết `Marshaller` (có sẵn `ProtoWriter`/`ProtoReader` mức thấp để mã hoá protobuf, không có codegen).
  Server dùng chung cổng với HTTP thường (`fallback(router)`), có h2c và TLS+ALPN. Ví dụ để học: `GrpcHelloExample` (server) và `GrpcHelloClientExample` (client, `GrpcChannel`); `GrpcEchoExample` là server dùng cho test.
  ```java
  GrpcServer grpc = GrpcServer.builder().unary(UNARY, (req, ctx) -> new Msg("echo:" + req.text())).addService(new HealthService()).build();
  grpc.bind(group, new InetSocketAddress(50051), null);
  try (GrpcChannel ch = GrpcChannel.forTarget("http://localhost:50051").build()) {
      Msg r = ch.unary(UNARY, new Msg("hi"), CallOptions.DEFAULT.withDeadline(Duration.ofSeconds(2))).join();
  }
  ```
  Đã đối chiếu với grpc-java (client và server) và @grpc/grpc-js (client và server): `interop/run-grpc.sh`.
  Thêm vào gRPC:
  *Header đầu của response*: `ctx.responseHeaders().put(..)` (gửi cùng message đầu tiên, hoặc cùng status nếu không có message); server hoãn head tới lúc đó, nên call lỗi ngay chỉ tốn một khối HEADERS (Trailers-Only).
  *Interceptor*: `GrpcServer.builder().intercept((method, ctx) -> ...)` (từ chối bằng `StatusException`, thấy từng message và status cuối; không sửa được message) và `GrpcChannel.forTarget(..).intercept(ClientInterceptor)`.
  *Retry / hedging / throttling*: `.retryPolicy(RetryPolicy.defaults())` (mặc định chỉ thử lại UNAVAILABLE, 3 lần, backoff có jitter) hoặc `.hedgingPolicy(HedgingPolicy.defaults())` (gửi song song sau `hedgingDelay`, lấy kết quả đầu tiên, huỷ phần còn lại), không dùng chung;
  `.retryThrottling(new RetryThrottling(10, 0.1))` chặn thử lại khi server đang lỗi liên tục. Deadline tính chung cho mọi lần thử. Chỉ thử lại khi chưa có message nào của response tới tay app và request còn nằm trong bộ đệm (`retryBufferBytes`, 256 KiB).
  Mặc định tắt vì thử lại/hedge call không idempotent có thể chạy hai lần.
  *Thử lại trong suốt*: kể cả khi không có policy, call mà server chắc chắn chưa xử lý (stream nằm sau mốc GOAWAY, `REFUSED_STREAM`) được gửi lại tối đa 2 lần, không tính vào `maxAttempts` (hữu ích khi rolling update).
  Server gRPC dùng `Http2Config.grpcDefaults()` (2000 RST_STREAM/s, 20000 control frame/s mỗi kết nối) vì client gRPC huỷ call là việc bình thường; HTTP/2 thường vẫn 200/s.
  *Service config JSON*: `.serviceConfig(json)` (`ServiceConfig`): timeout, retry/hedging, giới hạn kích thước message theo từng method (selector `{service, method}` > `{service}` > `{}`), `loadBalancingConfig`, `retryThrottling`, `healthCheckConfig`. Cái đặt tay trên builder thắng config.
  *Name resolver + load balancing*: `NameResolver.dns()` (mọi bản ghi A/AAAA, làm mới mỗi `resolveInterval`) / `fixed(..)` / tự viết; `LoadBalancing.PICK_FIRST` / `ROUND_ROBIN`; địa chỉ lỗi kết nối bị loại tạm (1 s, gấp đôi tới 30 s).
  `.healthCheck(interval)` hỏi `grpc.health.v1.Health/Check` từng địa chỉ và tránh những cái trả NOT_SERVING hoặc không phản hồi; server không có health service coi như khoẻ. Host trong target vẫn dùng cho `:authority` và kiểm tra chứng chỉ.
  *Per-RPC credentials*: `.callCredentials(CallCredentials.bearer(() -> token))` hoặc tự viết (bất đồng bộ, lấy lại cho mỗi lần thử); từ chối cấu hình trên `http://` trừ khi `allowCredentialsOverPlaintext()`.
  *Keepalive*: `.keepAlive(interval, timeout)` gửi HTTP/2 PING khi im lặng và đóng kết nối nếu không có gì trả lời (mặc định tắt; server có thể phạt ping quá dày).
  *gRPC-Web* (HTTP/1.1 hoặc HTTP/2; nhị phân `application/grpc-web[+proto]` và base64 `application/grpc-web-text[+proto]`): unary và server streaming, trailer nằm trong frame cuối của body; `allowCors(origin, headers..)` trả lời preflight.
  Chế độ text giữ lại phần dư < 3 byte tới lần ghi sau (như Envoy), nên 1–2 byte cuối của một message có thể chờ message kế tiếp. Trên HTTP/1.1 mỗi call đóng kết nối khi xong.
  *Reflection* (`ReflectionService`, v1 và v1alpha, kể cả extension): `grpcurl list` chạy ngay; `describe` và gọi bằng JSON cần `addDescriptorSet(bytes)` với `protoc --descriptor_set_out --include_imports` (thư viện không tự sinh được descriptor từ marshaller viết tay).
  *Channelz* (`new ChannelzService()`, `grpc.channelz.v1`): servers, client channels, subchannels và "socket" (kết nối đã mang call gRPC; server lưu theo địa chỉ remote, bỏ sau 5 phút im lặng), số call bắt đầu/thành công/thất bại, trạng thái kết nối, số message. Không báo trace và flow-control window. Đừng mở cho client không tin cậy (lộ địa chỉ peer).
  *Binary logging* (`BinaryLog.toFile(path, "*{h:256;m:256}")`, `.binaryLog(log)` trên cả server và channel): định dạng `grpc.binarylog.v1.GrpcLogEntry` có tiền tố độ dài; cấu hình kiểu `GRPC_BINARY_LOG_CONFIG` (`*`, `svc/*`, `svc/method`, `-loại trừ`, `{h;m:N}`). Ghi bằng luồng riêng; quá tải thì bỏ entry và đếm (`dropped()`), không làm chậm call.
  *xDS* (`GrpcChannel.forTarget("xds:///service").xdsBootstrap(json)` hoặc `GRPC_XDS_BOOTSTRAP[_CONFIG]`): ADS v3 SotW tới management server (Istio, Traffic Director, go-control-plane...); LDS→RDS→CDS→EDS, ACK/NACK, mở lại stream có backoff và vẫn route bằng snapshot cũ khi mất kết nối.
  Route theo path/prefix/regex, header (exact, prefix, suffix, contains, regex, present, range, `string_match`, invert), weighted clusters, timeout của route; chọn virtual host theo domain; cluster EDS và STATIC; endpoint có weight, bỏ UNHEALTHY/DRAINING, chỉ dùng priority tốt nhất; round robin có trọng số.
  Không hỗ trợ (resource bị NACK kèm lý do): aggregate cluster, redirect/direct_response, cluster_header, ring_hash/least_request, query-param match. Bỏ qua: LRS (báo tải), TLS/mTLS giữa các peer (transport_socket), circuit breaking, outlier detection, HTTP filters (RBAC, fault injection), delta xDS, xDS federation.
  Giới hạn còn lại của gRPC: `waitForReady`, service config lấy từ DNS TXT.
- **AMQP 0-9-1 client cho RabbitMQ** (`io.hydrangea.amqp`, không phụ thuộc thư viện ngoài): `AmqpConnection.connect(group, AmqpConfig.of(host, port))`, rồi `openChannel()`. Mọi lời gọi trả `CompletableFuture`;
  future và callback của consumer chạy trên event loop nên không được chặn. Có exchange / queue / binding (declare, delete, bind, unbind, purge), publish (cờ `mandatory` + `onReturn` cho message không route được),
  publisher confirms (`confirmSelect`), consume với ack / nack / reject và `basicQos`, `basicGet`, heartbeat, đóng kết nối êm, TLS (`AmqpConfig.withTls(ctx)`, có kiểm tra hostname), xác thực PLAIN.
  Message lớn tự cắt theo `frame-max`; message nhận về bị chặn bởi `maxMessageBytes` (mặc định 64 MiB) và bộ nhớ chỉ cấp phát theo byte thực sự đến, không theo kích thước khai báo.
  ```java
  AmqpConnection c = AmqpConnection.connect(group, AmqpConfig.of("localhost", 5672)).get();
  AmqpChannel ch = c.openChannel().get();
  String queue = ch.queueDeclare().get().name();          // queue do broker đặt tên, mất khi ngắt kết nối
  ch.basicQos(10).get();
  ch.basicConsume(queue, false, d -> { handle(d.body()); ch.basicAck(d.deliveryTag(), false); }).get();
  ch.basicPublish("", queue, false, BasicProperties.PERSISTENT, "hi".getBytes()).get();   // có confirmSelect() thì xong khi broker xác nhận
  ```
  *Back-pressure*: `basicPublish` không bao giờ chặn, nên producer không để ý tới `isWritable()` sẽ xếp dữ liệu trong bộ nhớ không giới hạn. `connection.whenWritable()` (cũng có trên `AmqpChannel` và `RecoveringChannel`)
  trả future hoàn thành khi hàng đợi ghi vơi xuống dưới ngưỡng thấp, hoặc hoàn thành ngay nếu đang ghi được; **thất bại nếu kết nối đóng trước** nên producer đang chờ không bao giờ treo.
  `onWritabilityChanged(Consumer<Boolean>)` báo từng lần đổi trạng thái. Vòng lặp mẫu: `while (c.isWritable()) { publish(); } c.whenWritable().thenRun(this::produce);` (đầy đủ trong `AmqpProducerExample`).
  Ngưỡng cao/thấp là `Options.highWaterMark/lowWaterMark` (64/32 KiB); bộ đệm socket của hệ điều hành nhận thêm vài MiB trước khi hàng đợi đầy, nên mỗi lượt publish liên tục có thể là vài message.
  *Tự kết nối lại*: `RecoveringConnection.connect(group, config, RecoveryPolicy.defaults())` (chờ tăng dần có jitter, `maxAttempts`; lần kết nối đầu không thử lại). Khi mất kết nối nó nối lại rồi khai báo lại exchange, queue, binding,
  mở lại mọi `RecoveringChannel` với `basicQos`, confirm mode và consumer (cùng consumer tag). Đối tượng channel ứng dụng đang giữ vẫn dùng được. Cần biết: trong lúc mất kết nối mọi lời gọi **thất bại ngay**;
  publish đang chờ xác nhận lúc đứt cũng thất bại (broker có thể đã nhận, nên gửi lại là *ít nhất một lần*); message chưa ack được broker giao lại với cờ `redelivered`; ack tag của kết nối cũ bị bỏ qua (tag mà ứng dụng thấy luôn tăng,
  không bao giờ trùng tag mới); queue do broker đặt tên đổi tên sau khi nối lại nhưng vẫn gọi được bằng tên cũ (`queueName(old)` cho tên hiện tại); khai báo mà broker giờ từ chối (queue đã tồn tại với tham số khác, 406) bị bỏ khỏi danh sách phục hồi và báo qua `RecoveryListener.declarationFailed`, việc nối lại vẫn tiếp tục; channel mà cấu hình riêng (consume, prefetch) bị từ chối thì đóng với lỗi của broker và consumer của nó được báo.
  Bỏ cuộc ngay khi bị từ chối đăng nhập (403 / 530). `RecoveryListener` báo mất kết nối, từng lần thử, thành công, bỏ cuộc.
  Kiểm chứng với RabbitMQ 3.13 thật trong Docker (`hydrangea-amqp/src/test/resources/amqp/start-broker.sh` dựng broker có cổng TLS; test tự bỏ qua nếu không có broker): kết nối, publish/consume, message 0 byte tới 5 MB, confirm, mandatory/return, lỗi 404/406 chỉ đóng channel,
  TLS (CA lạ bị từ chối, chứng chỉ của CA tin cậy nhưng sai tên máy bị từ chối, 3 MB qua TLS), heartbeat, broker giả độc hại (frame hỏng, 1 TB khai báo, im lặng, đổi phiên bản giao thức), nối lại qua proxy cắt được kết nối, `rabbitmqctl close_all_connections`,
  xoá user giữa chừng, và `docker restart` broker khi đang gửi/nhận 3000 message có xác nhận: 0 mất, 0 trùng.
  Ví dụ: `AmqpExample`, `AmqpProducerExample`. Chưa có: SASL khác PLAIN (EXTERNAL...), AMQP 1.0, RPC helper, nối lại qua nhiều địa chỉ broker.
- **MQTT client, 3.1.1 và 5.0** (`io.hydrangea.mqtt`, không phụ thuộc thư viện ngoài): `MqttClient.connect(group, MqttConfig.of(host, port))`, rồi `publish`, `subscribe`, `unsubscribe`, `disconnect`. Mặc định là 3.1.1; `.withVersion(5)` để dùng MQTT 5. Mọi lời gọi trả `CompletableFuture`;
  handler và listener chạy trên event loop nên không được chặn. QoS 0, 1, 2 đầy đủ (QoS 2 gửi: PUBLISH → PUBREC → PUBREL → PUBCOMP; QoS 2 nhận: giao đúng một lần, PUBLISH lặp chỉ được trả lời), retained, will, wildcard `+` / `#` (kiểm tra filter, quy tắc `$`),
  keep-alive (PINGREQ sau nửa chu kỳ im lặng, broker im quá 1,5 chu kỳ thì coi là chết), TLS có kiểm tra hostname, user/password, `maxPacketBytes` (gói quá lớn bị từ chối chỉ từ header), `maxInflight` / `maxQueued`.
  ```java
  MqttClient c = MqttClient.connect(group, MqttConfig.of("localhost", 1883).withClientId("me")).get();
  c.subscribe("sensors/+/temp", QoS.AT_LEAST_ONCE, m -> handle(m.topic(), m.payload())).get();   // trả QoS broker cấp
  c.publish("sensors/kitchen/temp", "21.5".getBytes(), QoS.AT_LEAST_ONCE).get();                 // xong khi nhận PUBACK
  ```
  *MQTT 5* (`withVersion(5)`): **reason code** (publish/subscribe bị từ chối thì future thất bại với `MqttException.reasonCode()`, ví dụ 0x87 không được phép, 0x97 vượt hạn mức; mã tạm thời thì `retriable()`), **thuộc tính của message** (`MqttProperties`: content type, response topic + correlation data cho request/response,
  user property, payload format, message expiry), **tuỳ chọn subscribe** (`SubscribeOptions`: no-local, retain-as-published, retain handling), **shared subscription** (`$share/nhóm/filter`), **subscription identifier** (client tự gắn id cho từng subscription và định tuyến message theo id broker gửi về,
  nên các filter chồng lấn không còn giao trùng như MQTT 3.1.1), giới hạn của broker trong CONNACK (`client.serverInfo()`: receive maximum được tôn trọng khi gửi, maximum QoS, retain, maximum packet size; vi phạm thì `publish` thất bại ngay với reason code tương ứng),
  server keep-alive, client id do broker cấp (giữ nguyên khi nối lại để phiên còn dùng được), session expiry (`MqttConfig.V5`), will delay, topic alias nhận, DISCONNECT từ broker (đọc lý do; 0x8E "phiên bị chiếm" thì không nối lại để khỏi giành lại phiên).
  *Thêm cho MQTT 5*: **xác thực mở rộng** (`MqttConfig.V5.withAuthenticator(...)`: giao diện `MqttAuthenticator` chạy trao đổi thách thức/đáp trả bằng gói AUTH ngay trong CONNECT, kiểm chứng bằng lời cuối của broker trong CONNACK để xác thực hai chiều; `client.reauthenticate()` chạy lại trên kết nối đang mở, tin vẫn chạy trong lúc đó; kèm sẵn `ScramSha256` theo RFC 5802/7677, khớp ví dụ của RFC 7677),
  **topic alias khi gửi** (`V5.withOutgoingTopicAliases(true)`: topic đã gửi một lần thì đi lại bằng số 2 byte, bảng alias của broker đầy thì thay cái dùng lâu nhất, mỗi kết nối bắt đầu lại, tin gửi lại sau khi nối lại khai báo lại alias), **message expiry đếm ngược** (thời gian tin chờ trong hàng đợi hoặc trước khi gửi lại bị trừ khỏi khoảng hết hạn; tin hết hạn khi còn chờ thì bị bỏ và future thất bại,
  còn tin đã gửi một lần mà hết hạn thì vẫn phải gửi lại với khoảng 1 giây vì số hiệu gói của nó không thể bỏ, và 0 nghĩa là "không hết hạn" với một số broker), và **request/response** (`client.request(topic, payload, qos, timeout)` tự subscribe một response topic, gắn correlation id, ghép câu trả lời; `client.reply(request, payload, qos)` ở phía trả lời).
  *Tự kết nối lại có sẵn* (`MqttConfig.reconnect`, mặc định `Backoff.defaults()`; `null` để tắt): lần kết nối đầu thất bại thì trả lỗi, không thử lại; sau khi đã online thì mất kết nối sẽ thử lại có jitter. Tin QoS 1/2 chưa được xác nhận **ở lại trong client**:
  nếu broker còn phiên (`cleanSession=false`) thì gửi lại với cờ DUP (tin QoS 2 đã qua PUBREC tiếp tục từ PUBREL, không PUBLISH lại); nếu broker mất phiên thì chúng **thất bại** với `MqttException` retriable (gửi lại có thể làm QoS 2 trùng).
  Tin nhận lúc đang mất kết nối thì xếp hàng; QoS 0, `subscribe`, `unsubscribe` lúc mất kết nối thất bại ngay. Subscription tự đăng ký lại khi broker mất phiên (giữ nguyên tuỳ chọn và id; `MqttListener.resubscribeFailed` nếu bị từ chối). Mã từ chối đăng nhập, giao thức, id bị loại: không thử lại.
  Trạng thái chỉ nằm trong bộ nhớ: **không sống sót qua việc khởi động lại tiến trình**. Với MQTT 3.1.1, filter chồng lấn: broker có thể gửi một bản cho mỗi subscription và client không biết bản nào của filter nào, nên mỗi handler khớp nhận mọi bản (tránh filter chồng lấn, hoặc dùng MQTT 5).
  *Back-pressure*: `publish` không chặn; `client.whenWritable()` (core: `Connection.whenWritable()`) hoàn thành khi hàng đợi ghi vơi đi, thất bại nếu mất kết nối.
  *Transport thay được* (`MqttTransport`): mặc định TCP (+TLS); `MqttWebSocket` (cùng module) cho **MQTT qua WebSocket** (`ws://` và `wss://`, subprotocol `mqtt`):
  `MqttConfig.of(host, port).withTransport(MqttWebSocket.of("wss://broker/mqtt"))`. Mọi thứ khác giữ nguyên (3.1.1 và 5, nối lại, `whenWritable()`); gói MQTT có thể bị chia qua nhiều message WebSocket hoặc nhiều gói chung một message; gói lớn hơn 256 KiB gửi dưới dạng một message phân mảnh
  (không dính giới hạn `maxMessageBytes` của WebSocket); message văn bản là lỗi giao thức.
  Kiểm chứng với Mosquitto 2.1.2 thật trong Docker (`hydrangea-mqtt/src/test/resources/mqtt/start-broker.sh`: cổng thường, cổng có mật khẩu + ACL, cổng TLS, cổng WebSocket; test tự bỏ qua nếu không có broker): mọi mức QoS, retained (kể cả xoá), will (bị hủy khi DISCONNECT, phát khi mất kết nối, will delay), phiên bền vững giữ tin lúc offline,
  bị chiếm phiên, 5000 tin QoS 1 và 1000 tin QoS 2 đúng thứ tự / đúng một lần, 8 luồng cùng publish, tin tới 1,5 MB, unicode, mật khẩu sai, ACL (PUBACK / PUBREC 0x87 thật), TLS (CA lạ bị từ chối), proxy cắt kết nối giữa 3000 tin QoS 1 (0 mất) và cắt "im lặng" (keep-alive phát hiện);
  MQTT 5: thuộc tính đi qua broker, request/response, shared subscription (200 việc chia cho hai worker, không trùng), no-local, retain handling, retain-as-published, subscription id với filter chồng lấn, session expiry, client id do broker cấp, bị chiếm phiên (0x8E), message expiry, will delay, nối lại giữ tuỳ chọn subscription;
  WebSocket: cả hai phiên bản, lẫn với client TCP, message 1,5 MB hai chiều, 2000 tin trong bay, đứt kết nối rồi nối lại, broker không nói WebSocket.
  Test không cần broker (`MqttProtocolTest` 47 và `Mqtt5ProtocolTest` 30, peer giả điều khiển từng byte): 21 kiểu gói hỏng và 11 kiểu khối thuộc tính hỏng, gói quá lớn, gói bị chia từng byte hoặc dán nhiều gói, từng trạng thái QoS 1/2, mọi reason code của CONNACK / PUBACK / SUBACK / DISCONNECT, DUP khi gửi lại, mất phiên, hết kiên nhẫn kết nối lại.
  Chưa có: lưu trữ tin chưa xác nhận ra đĩa, nối lại qua nhiều địa chỉ broker. Ví dụ: `MqttExample`, `Mqtt5Example` (có thể chạy qua WebSocket).
- **Unix domain socket**: truyền `UnixDomainSocketAddress` cho `Server.bind` / `Client.connect` (kể cả HTTP). File socket tự xoá khi `Server.close()`.
- **Multicast**: `UdpSocket.bind(..., new UdpSocket.Config(1024, true, StandardProtocolFamily.INET), listener)` rồi `joinGroup(group, networkInterface)`; cấu hình bằng `setOption(IP_MULTICAST_IF/TTL/LOOP, ...)`.
- **Server / Client**: bind đồng bộ (lỗi bind ném ngay), connect trả `CompletableFuture<Connection>` có timeout.
- **codec**: `FramingHandler`, `LineHandler`, `LengthPrefixedHandler` (kiểu Handler đơn giản, không cần Pipeline).

## Hiệu năng
Đo trên một máy 8 nhân (macOS, JDK 25), tải và server cùng máy, mỗi ca 12 giây sau 8 giây khởi động; chỉ so sánh tương đối được. Mọi ca 0 lỗi.
Các mục so với Netty/Undertow trên k8s và HTTP/1.1 cục bộ ghi môi trường riêng ngay trong từng mục. Số liệu thô nằm ở `benchmark/`; chạy lại bằng `benchmark/run-http.sh`, `run-h2.sh`, `run-grpc.sh`.

- **HTTP/1.1 so với Netty, máy cục bộ** (8 nhân, JDK 25, server 4 thread I/O, client cùng máy, 3 vòng lấy vòng trung vị, `benchmark/RESULTS-HTTP-final.md`): GET 13 B với 64 kết nối 202k so với 187k req/s (+8%), với 1000 kết nối 199k so với 188k (+6%);
  POST echo 1 KiB 194k so với 175k (+11%); tải 1 MiB 9,8 so với 7,3 GB/s; WebSocket echo 64 B 202k so với 186k. CPU mỗi request 16,1 so với 17,4 µs.
- **HTTP/1.1 so với Netty, trên k8s** (2 CPU, 2 thread I/O, Netty 4.2.10 với `HttpServerCodec` + `HttpObjectAggregator` không tinh chỉnh, 3 vòng xen kẽ, `benchmark/RESULTS-K8S.md`): GET `/plain`, route có tham số, WebSocket và tải lớn **ngang nhau**
  (chênh nhỏ hơn dao động giữa các vòng của cùng một server nên không phải kết quả). Khác biệt rõ chỉ ở POST có body (+13%, nhất quán giữa các vòng) và `/json` (176k so với 144k). p99 của Hydrangea cao hơn Netty ở đa số dòng, trong khoảng 15%.
  Node dùng chung với tải khác của namespace nên số tuyệt đối nhiễu.
- **So với Undertow 2.3.18 trên k8s** (0,5 CPU, 1 thread I/O, cùng pod limit, 3 vòng xen kẽ, `benchmark/RESULTS-K8S-HTTP-UNDERTOW.md`, `RESULTS-K8S-TLS-UNDERTOW.md`):
  - HTTP/1.1, handler chạy trên thread I/O: **ngang nhau**. GET 16 / 64 / 256 kết nối: 47,0k / 51,2k / 44,7k so với 47,3k / 48,4k / 40,3k req/s (Undertow đã tinh chỉnh); POST 1 KiB 44,1k so với 41,0k (+7%). Qua TLS cũng ngang cho GET, +13% cho POST.
  - HTTP/2 không TLS: Hydrangea nhanh hơn 3,4–3,5 lần cho GET (145k so với 43k, 157k so với 45k) và khoảng 8 lần cho echo 1 KiB (105k so với 12,9k). Qua TLS: 2,8 lần (GET) và 4,9 lần (echo).
  - Undertow với `dispatch()` sang worker pool (cách viết thường gặp của code ứng dụng) chỉ còn khoảng một nửa thông lượng; Hydrangea hơn 1,7–2,1 lần, nhưng đó là so hai mô hình thread chứ không phải hai bộ phân tích.
  - Lưu ý khi đọc phần HTTP/2: Undertow dùng cửa sổ stream mặc định 64 KiB, và đặt 1 MiB thì gặp lỗi (không gửi WINDOW_UPDATE ở mức kết nối) nên không dùng được; chưa thử các tinh chỉnh sâu hơn (bố trí worker XNIO, buffer pool). Khoảng cách GET (không có body) là chi phí CPU mỗi request.
  - Chưa đo với Undertow: WebSocket/SSE, servlet, nhiều CPU hơn, bộ nhớ.
- **HTTP/2 so với Netty** (`Http2FrameCodec`, cùng tải từ client Netty): GET 13 B ngang nhau (381k so với 385k req/s với 4×16 stream; 541k so với 543k với 16×64),
  POST echo 1 KiB 353k so với 276k, tải 1 MiB 3,99 so với 2,24 GB/s. CPU mỗi request của Hydrangea thấp hơn ở các ca nhỏ (3,1–3,6 so với 4,2–7,1 µs).
- **gRPC server so với grpc-java** (cùng client grpc-java): unary 16 B 277k so với 249k req/s (64 lệnh đồng thời), 322k so với 280k (512);
  unary 4 KiB 174k so với 142k (512); streaming 100×1 KiB 11,9k so với 7,4k stream/s (64). unary 64 KiB 19,8k so với 21,0k (64 lệnh) và 18,6k so với 20,2k (512), tức thua khoảng 6–8% (chênh giữa các lần chạy cỡ ±8%).

Mất kết nối: query đang chờ thất bại (`PgException.retriable()` false: có thể đã chạy). Kiểm chứng với PostgreSQL 16 thật (`hydrangea-postgres/src/test/resources/postgres/start-postgres.sh`, 3 kiểu đăng nhập; `-Dpg.host=... -Dpg.remote=true` để chạy trên DB khác, bỏ qua các test tạo bảng hoặc thử sai mật khẩu; đã chạy với PostgreSQL 17.5; TLS cần `make-certs.sh` và hai container TLS trong `start-postgres.sh`; PgBouncer cần `start-pgbouncer.sh`) và server giả gửi dữ liệu sai; so với pgjdbc + HikariCP trong `benchmark/RESULTS-POSTGRES.md`: **ngang nhau khi số kết nối bằng số luồng gọi** (CPU mỗi query tương đương), **nhanh hơn 4-6 lần khi luồng gọi nhiều hơn kết nối** (nhờ pipeline, không phải nhờ event loop; 8-9 lần qua mạng có RTT 12 ms đến một PostgreSQL 17.5 thật), transaction lúc đầu chậm hơn 17-23% vì chờ BEGIN, đã sửa bằng cách gửi BEGIN cùng câu đầu và đo lại thì ngang pgjdbc (khác biệt giữa hai phiên đo lớn hơn cả chênh lệch, xem file kết quả). **TLS** (`PgConfig.withTls(sslContext)`: gửi `SSLRequest`, nâng cấp, kiểm tra chứng chỉ theo tên host; server trả "không" là lỗi chứ không lùi về văn bản thô; byte thừa sau `S` bị từ chối để chặn CVE-2021-23222). **COPY** (`copyIn(sql, Iterable<byte[]>)` hoặc handle `PgCopyIn` có `write` với backpressure/`finish`/`abort`, `copyOut(sql, sink)`; text, CSV và binary đi qua dưới dạng byte; `COPY ... FROM STDIN` giữ riêng kết nối đến khi xong, các query khác chờ rồi chạy theo thứ tự). **Function và procedure**: gọi bằng chính câu SQL, `SELECT ham($1, $2)` hoặc `SELECT * FROM ham_tra_bang($1)` cho function (kể cả `RETURNS TABLE`, `SETOF`, tham số `OUT`), `CALL thu_tuc($1::int, ...)` cho procedure (giá trị `OUT`/`INOUT` trả về là một dòng; procedure có `COMMIT` bên trong chạy được khi gọi ngoài transaction). Không có cú pháp `{call ...}` của JDBC; tham số kiểu String không có kiểu nên cần ép kiểu (`$1::int`) khi hàm bị nạp chồng. `RAISE EXCEPTION ... USING ERRCODE/DETAIL/HINT` đến nơi dưới dạng `PgException` với `sqlState()`, `detail()`, `hint()`; `RAISE NOTICE` đến `PgListener.onNotice`. Kết quả kiểu mảng hoặc composite trả về dạng text. **Kết quả lớn và đọc theo luồng**: một kết quả được giữ nguyên trong bộ nhớ nên có giới hạn (`PgConfig.withResultLimits(maxRows, maxBytes)`, mặc định 1 triệu dòng và 256 MiB; vượt thì query lỗi, phần còn lại được đọc và bỏ, kết nối vẫn ổn); `stream(fetchSize, sql, ...)` đọc theo từng mảnh (cursor: server chỉ gửi mảnh kế tiếp khi người gọi đã lấy mảnh trước, bộ nhớ cỡ hai mảnh dù kết quả lớn đến đâu; kết nối thuộc về stream đến khi nó kết thúc hoặc `close()`). **Batch**: `executeBatch(sql, danh sách bộ tham số)` chạy một câu nhiều lần chỉ với một `Sync` (một vòng mạng, nguyên tử, báo số dòng từng mục và mục nào lỗi): nhanh hơn batch mặc định của pgjdbc 1,7 lần nhưng chậm hơn `reWriteBatchedInserts` 2 lần; nạp nhiều dòng thì dùng `INSERT ... SELECT FROM unnest($1::int[], $2::text[], ...)` với tham số mảng (645 k dòng/giây so với 671 k của pgjdbc, nhanh hơn `reWriteBatchedInserts` 558 k) hoặc COPY. **Binary** (`PgConfig.withBinaryTransfer`, mặc định bật): sau khi server đã mô tả statement, tham số có dạng binary tương ứng với kiểu server báo (số, bool, uuid, bytea không bị nhân đôi vì hex, ngày giờ, numeric, mảng) được gửi binary, và kết quả được yêu cầu binary cho các cột mà dạng text tái dựng được chính xác (bool, số nguyên, numeric, uuid, bytea, mảng của chúng), nên cái người gọi thấy không phụ thuộc định dạng (số thực, ngày giờ, json giữ text); lần chạy đầu của mỗi statement luôn là text. Đo lần đầu cho thấy binary **không** giúp ích (còn chậm hơn ở `unnest`), JFR chỉ ra thời gian đi vào việc dựng text mảng dù sẽ gửi binary, sao chép danh sách, và cấp phát từng phần tử; sau khi sửa ba điểm đó binary nhanh hơn text 16% ở bài `unnest` và không đổi gì ở truy vấn trả vài cột số nguyên (xem `benchmark/RESULTS-POSTGRES.md`). **Mảng**: kết quả kiểu mảng thành `List` (lồng nhau nếu nhiều chiều, `getList(i, Integer.class)`), và `List`/mảng Java gửi được làm tham số (`= ANY($1)`, `unnest($1::int[])`). **Pool**: hàng đợi chờ kết nối (`PgPoolOptions.acquireTimeout`, `maxWaiters`), thay kết nối chết kể cả khi không có tải, `maxLifetime`, ping kết nối rảnh, `TxOptions` (mức cô lập, read-only, deferrable) và `transactionWithRetry` (xung đột serialization, deadlock). **Độ bền**: soak test 180 giây (117 421 thao tác trộn đủ loại, 0 lỗi, heap phẳng 3 MB, statement chuẩn bị chặn ở kích thước cache) và fuzz bộ phân tích (900 luồng dữ liệu rác); chúng tìm ra bốn lỗi mà test thường không thấy, xem `benchmark/RESULTS-POSTGRES.md`. **Chạy trong k8s** (pod 2 CPU, cùng mạng với PostgreSQL 17.5, độ trễ khoảng 0,1 ms, chỉ đọc): Hydrangea nhanh hơn biến thể pgjdbc tốt nhất 1,1–1,2 lần khi mỗi luồng có một kết nối, 2,5–4,6 lần khi luồng gọi nhiều hơn kết nối, và 1,8–2 lần ở 32 kết nối cho 32 luồng, với CPU mỗi query ít hơn 1,3–4,5 lần; pgjdbc kèm HikariCP là biến thể chậm nhất (xem `benchmark/RESULTS-POSTGRES.md`). **Ghi bền vững (Linux trong Docker, `fsync` bật)**: lợi thế của pipeline thu hẹp mạnh khi server phải ghi đĩa: `insert` ở 8 kết nối 64 luồng chỉ nhanh hơn 1,3 lần (23 k so với 17,7 k) trong khi với `fsync` tắt là 2 lần; ngang pgjdbc khi mỗi luồng có một kết nối và ở transaction (chênh lệch trong 6–7%), với CPU mỗi lệnh ít hơn. Với `fsync` tắt, pgjdbc kèm HikariCP đạt thông lượng `tx` cao hơn ở 8:64 (38,6 k so với 23,3 k) nhưng với p99 khác hẳn (21–26 ms trong khi p50 chỉ 0,13 ms): nhiều khả năng là sự bất công của pool (vài luồng giữ kết nối, các luồng khác chờ), chưa kiểm chứng. **Giới hạn thời gian** (`PgConfig.withQueryTimeout(...)` hoặc `query(Duration, sql, ...)`): hết hạn thì future thất bại ngay với `PgException.isTimeout()` và server được yêu cầu huỷ bằng `CancelRequest` trên một kết nối riêng (pid và secret từ `BackendKeyData`; cũng qua TLS). Vì các query được pipeline, cancel chỉ gửi khi query hết hạn là query server đang chạy, nên không huỷ nhầm query của người khác; query còn xếp hàng chỉ bị huỷ khi đến lượt, và nếu cancel vẫn trúng query kế tiếp thì query đó nhận lỗi `retriable`. **Bảng đổi cấu trúc dưới statement đã cache** (`0A000 cached plan must not change result type`): client bỏ statement khỏi cache và chạy lại một lần nếu không ở trong transaction. Đã đo: TLS tốn thêm khoảng 4 µs CPU mỗi query (không đổi thông lượng khi độ trễ mạng là giới hạn), COPY 1 triệu dòng ngang `CopyManager` của pgjdbc (chênh lệch nằm trong nhiễu). **Tự nối lại** (`PgConfig.withReconnect(Backoff)`, mặc định tắt; `PgPool` tự thay kết nối nên tắt nó cho các kết nối của mình): mất kết nối thì chờ theo back-off rồi nối lại, báo qua `PgListener` (`onClose`, `onReconnecting`, `onReconnected`, `onGaveUp`); query đang chờ thất bại, query gửi trong lúc mất kết nối thất bại ngay và `retriable`; phiên mới nên cache statement bắt đầu lại, các kênh đăng ký bằng `listen(channel)` được `LISTEN` lại, còn `SET`, bảng tạm và transaction thì mất: nếu mất kết nối giữa transaction thì query đầu tiên của phiên mới thất bại một lần với lỗi nói rõ điều đó thay vì chạy tiếp như thể transaction còn mở. **PgBouncer** (chế độ transaction, thử với 1.26): mọi thứ chạy kể cả cache statement khi PgBouncer biết prepared statement (`max_prepared_statements`, từ 1.21); bản cũ hơn thì dùng `withStatementCacheSize(0)`; `LISTEN` và `SET` cần kết nối trực tiếp hoặc session pooling (`start-pgbouncer.sh` dựng hai bản để thử). Chưa có: replication, kiểu composite/range/hstore (trả text), TLS client certificate, channel binding, Kerberos, nhiều host. Cancel nhầm query khác: với query pipeline, cancel của query hết hạn có thể trúng query kế tiếp; client tự chạy lại khi an toàn, còn COPY, stream và transaction thì nhận lỗi `retriable` (xem javadoc). Ví dụ: `PgExample`.
- **MySQL client** (`io.hydrangea.mysql`, không phụ thuộc thư viện ngoài; không phải driver JDBC): `MyClient.connect(group, MyConfig.of(host, 3306, user, db).withPassword(...))` rồi `query("... ? ...", params)`. Không có tham số thì đi bằng `COM_QUERY` (text); có tham số thì qua prepared statement phía server và giao thức binary (`COM_STMT_PREPARE/EXECUTE`, cache LRU theo kết nối, `withStatementCacheSize(0)` để đóng ngay sau mỗi lần chạy); `queryText`/`queryPrepared` ép một trong hai đường. **Một kết nối dùng chung cho mọi luồng**, lệnh được ghi nối tiếp (server MySQL xử lý tuần tự và trả lời theo thứ tự; khác PostgreSQL là không có `Sync` riêng, nhưng mỗi câu trả lời bằng OK hoặc gói lỗi riêng nên lỗi của một câu không ảnh hưởng câu sau); lần dùng đầu của một statement phải chờ câu trả lời `PREPARE` (lấy id) nên các lệnh phía sau chờ theo để giữ thứ tự. Các record cấu hình từng in mật khẩu qua `toString()`, đã che.

Lấy bằng `PgPool.create(...).join().asSql()` hoặc `MyPool.create(...).join().asSql()` (cũng có `PgClient.asSql()`, `MyClient.asSql()`), rồi code repository viết một lần: `execute("... ? ...", params)` (một tên cho SELECT lẫn INSERT/UPDATE/DDL, như JDBC; các lớp riêng vẫn gọi `query`) (placeholder `?` cho cả hai; với PostgreSQL client đổi thành `$n` ngoài chuỗi, định danh, chú thích và dollar-quote, `??` là một dấu `?` thật cho toán tử JSON, như pgjdbc), `transaction(tx -> ...)`, `transaction(SqlIsolation, readOnly, ...)`, `transactionWithRetry(n, ...)`; `SqlRow` có getter theo chỉ số và tên (`getString`, `getInt`, `getLong`, `getDouble`, `getBoolean`, `getBigDecimal`, `getBytes`, `getLocalDate`, `getLocalDateTime`, `getObject`, `isNull`); `SqlResult` có `rows()`, `first()`, `columnNames()`, `affectedRows()`; `SqlException` (lớp cha của `PgException` và `MyException`) phân loại `isDuplicateKey()`, `isRetriableServerError()` (serialization failure, deadlock), `isTimeout()`, `retriable()`, `sqlState()`. Giao diện cố ý nhỏ: những gì khác nhau giữa hai DB không bị che (SQL như `RETURNING`/`ON CONFLICT` so với `ON DUPLICATE KEY`, khoá sinh ra: `RETURNING id` so với `MyResult.lastInsertId()`, mức cô lập mặc định, DDL trong transaction, ánh xạ kiểu của `getObject`), và COPY, LISTEN, mảng, stream, batch, multi-result vẫn nằm trên `PgClient`/`MyClient`. Cùng một kịch bản test chạy trên cả hai (`PgSqlTest`, `MySqlTest`), ví dụ `SqlExample` chạy cùng lớp `Accounts` trên cả hai DB.
- **Kafka client** (`io.hydrangea.kafka`, không phụ thuộc thư viện ngoài): `KafkaClient.create(group, KafkaConfig.of("host:9092"))` rồi `producer(...)`, `consumer(...)`, `createTopic`. **Producer**: `send` trả `CompletableFuture<RecordMetadata>` từ mọi luồng (kể cả virtual thread), gom batch theo partition (`linger`, `batchBytes`), partitioner murmur2 giống client Java, `acks` 0/1/-1, nén gzip, `flush()`, giới hạn bộ nhớ (`bufferBytes`: quá thì lỗi, không phình), retry có backoff; **idempotent theo mặc định** (producer id + sequence, `acks=-1`, tối đa 5 batch bay mỗi partition, không trùng không đảo; `withoutIdempotence()` để dùng `acks` 0/1, khi đó mỗi partition một batch bay; cần Kafka 0.11 trở lên). **Consumer**: `assign` hoặc `subscribe` với **consumer group** (JoinGroup/SyncGroup/Heartbeat, thuật toán range, rebalance eager có `RebalanceListener`, commit/auto-commit, `seek`, `poll` trả future). SASL/PLAIN; TLS nối dây như Redis nhưng chưa thử với broker Kafka thật. Kiểm chứng với Kafka 3.9.0 thật (`hydrangea-kafka/src/test/resources/kafka/start-kafka.sh`) và broker giả; so với `kafka-clients` 3.9.0 trong `benchmark/RESULTS-KAFKA.md` (cùng cấu hình mặc định idempotent, 3 vòng xen kẽ, Docker trên macOS): produce 3 partition 1,93 M so với 1,61 M records/s, nhiều virtual thread dùng chung một producer 2 lần (723 k so với 359 k) với p99 thấp hơn 2 lần, consume 5,6 M so với 3,9 M, độ trễ end-to-end p50 0,3 ms so với 0,5 ms, CPU client mỗi record ít hơn một nửa; 1 partition ngang hoặc nhỉnh hơn khi đo xen kẽ có kiểm soát (1,70 M so với 1,41 M) dù bộ 3 vòng cho kết quả ngược (nhiễu); **còn thua** khi chỉ một batch bay mỗi partition, không idempotent (17% trong bộ 3 vòng, chưa đo lại có kiểm soát). Thông lượng dao động ±40% giữa các lần chạy. Chưa có: transaction, nén snappy/lz4/zstd, SCRAM/OAuth, cooperative rebalance, static membership, regex subscription, tự rebalance khi topic thêm partition, đọc read-committed. Chỉ nói các phiên bản API cũ (Produce v3, Fetch v4...) nên chạy với Kafka 0.11 đến 3.x; chưa thử Kafka 4.x. Ví dụ: `KafkaExample`.
- **MQTT client so với Eclipse Paho 1.2.5** (`MqttAsyncClient`; cùng một Mosquitto 2.1.2 trong Docker, JVM client chạy trong container thứ hai dùng chung network namespace với broker, tức Linux, loopback trong VM Docker; 3 vòng xoay thứ tự; `benchmark/RESULTS-MQTT.md`).
  Paho đo hai biến thể: như phát hành, và đặt `TCP_NODELAY` (Paho không có tuỳ chọn này nên Nagle luôn bật). Thông lượng đầu-cuối (publisher bị giới hạn bởi cửa sổ và bởi số tin chưa tới subscriber, nên không tin nào bị broker bỏ): QoS 1 khoảng 3,8 lần (258k so với 67k msgs/s) với 13% CPU mỗi tin,
  QoS 2 khoảng 4,0–5,1 lần, tin 64 KiB khoảng 24 lần (**đã tìm ra nguyên nhân**: `CountingInputStream` của Paho 1.2.5 chỉ cài `read()` nên đọc payload từng byte, hai lần cho mỗi tin nhận, đo riêng 8,9 ns/byte tức 580 µs cho 64 KiB so với 0,9 µs; chỉ tốn ở phía nhận, và là tính chất của phiên bản này chứ không phải của Paho nói chung), 100 kết nối 9,4 lần so với Paho thường (233k so với 25k; mở 100 kết nối mất 0,1 s so với 31,8 s, Paho ~320 ms mỗi kết nối, chưa rõ lý do) và
  1,34 lần so với Paho đặt NODELAY (Nagle làm Paho chậm 7 lần ở đây). Thread: 11–15 so với 406–410. Độ trễ từng tin một: Hydrangea thấp hơn nhưng chỉ hơn chục đến vài chục µs (QoS 1 p50 70 so với 85 µs). QoS 0: Hydrangea nhận 546k msgs/s và không mất tin (producer chờ `whenWritable()`),
  Paho gửi nhanh hơn nhưng broker bỏ phần lớn (vòng 1: 7,9M trên 10,5M tin bị mất), nên con số "gửi xong" của QoS 0 không phải lợi thế của Hydrangea.
  *Chạy lại với MQTT 5 (Paho `mqttv5.client`) và MQTT qua WebSocket* (`GROUP=v5` / `GROUP=v5ws` trong `mqtt-bench.sh`): MQTT 5 qua TCP gần như lặp lại kết quả 3.1.1 (QoS 1 4,0 lần, 64 KiB 23,7 lần, 100 kết nối 8,6 lần; QoS 2 7,4 lần vì client v5 của Paho chậm hơn client 3.1.1 của nó ở QoS 2); qua WebSocket cả hai chậm đi, Hydrangea còn 47% tốc độ TCP ở QoS 1, Paho 73%, nên tỷ lệ còn 2,6 lần (64 KiB 33 lần, 100 kết nối 2,2 lần). Độ trễ p50 thấp hơn 20–45% ở mọi nhóm. Hai lượt `paho5-ws` QoS 0 bị lỗi lúc đóng kết nối (lỗi của harness hoặc Paho) và không có số.
  Giới hạn quan trọng: Mosquitto đơn luồng chạy ~85–88% một nhân trong các lượt của Hydrangea, nên broker gần chạm trần; chạy client trên máy Mac qua cổng chuyển tiếp của Docker Desktop cho kết quả khác hẳn ở độ trễ QoS 1 từng tin một (Hydrangea p90 ~41 ms do kẹt Nagle/delayed ACK trong lớp chuyển tiếp, Paho thì hiếm gặp; **chưa rõ vì sao Hydrangea nhạy hơn**), chi tiết ở tài liệu kết quả.
- **Chạy lại benchmark HTTP, HTTP/2, gRPC sau khi tách module và thêm `whenWritable()` vào core** (`benchmark/RESULTS-RERUN.md`; cùng máy, cùng script và tham số như bản cũ 20–21/10): không có suy giảm ngoài nhiễu. Hôm nay cả máy chậm hơn 3–8% với mọi server (Netty cũng vậy), nên so **tỷ lệ với đối thủ trong cùng lượt chạy**:
  HTTP/1.1 và WebSocket Hydrangea/Netty 1,04–1,12 trước và 1,08–1,12 nay; HTTP/2 hỗn hợp trong khoảng 7% (tải 1 MiB 1,78 → 1,66; echo 1 KiB 1,28 → 1,22; plain 1,00 → 0,98 và 0,99 → 1,11); gRPC với bộ sinh tải grpc-java: server Hydrangea 0,97–1,18 lần số cũ, server grpc-java 0,99–1,21 lần, tỷ lệ giữa hai bên giữ 1,1–1,25 (unary nhỏ) và khoảng 1,7 (server streaming).
  Không tách được thay đổi nào gây ra chênh lệch nào (tất cả cùng nằm ở phía "nay"). Các dòng gRPC dùng bộ sinh tải Hydrangea tăng 1,2–3,4 lần ở cả hai server nên baseline cũ của phần đó thuộc về client cũ hơn; không dùng chúng để so server.
- Những gì làm nên khác biệt, tìm bằng JFR: gộp mọi `write` trong cùng một lần đọc thành một lần flush (một syscall cho nhiều phản hồi), gộp các ghi nhỏ liên tiếp của một stream HTTP/2 thành một khung DATA,
  tra HPACK bằng map thay vì quét bảng và cache chuỗi đã mã hoá.

## QUIC (thử nghiệm, nền của HTTP/3)
`io.hydrangea.quic`: server QUIC v1 (RFC 9000/9001/9002) trên `UdpSocket`, TLS 1.3 tối thiểu tự viết trên JCA (x25519, TLS_AES_128_GCM_SHA256, chứng chỉ ECDSA P-256 hoặc RSA-PSS, ALPN), điều khiển tắc nghẽn NewReno, phát hiện mất gói, flow control, nhiều stream, key update, Version Negotiation.
```java
QuicServer.bind(group, new InetSocketAddress(4433), QuicConfig.fromKeyStore(store, "alias", password, List.of("echo")), new QuicHandler() {
    public void onStreamData(QuicConnection c, long streamId, byte[] data, boolean fin) { c.send(streamId, data, fin); }
});
```
Ví dụ chạy được: `QuicEchoExample`. Kiểm chứng với `aioquic` (client QUIC độc lập, bỏ qua nếu máy không có `python3` + `aioquic`), vector RFC 9001, fuzz datagram. Retry / address validation có sẵn (`withRetry(true)`). *Chưa có*: 0-RTT, connection migration, stateless reset, delayed ACK, client QUIC, HelloRetryRequest, các nhóm khóa khác x25519, PMTU discovery (gói tin 1200 byte). Đừng dùng cho production. Chi tiết: `QUIC-STATUS.md`.

### HTTP/3 (thử nghiệm)
`Http3Server` chạy chính `HttpHandler`/`HttpRouter` đang phục vụ HTTP/1.1 và HTTP/2 qua QUIC (ALPN `h3`): khung HTTP/3 (RFC 9114), QPACK (RFC 9204) với bảng động tắt, stream điều khiển.
```java
Http3Server.bind(group, new InetSocketAddress(4433), QuicConfig.fromKeyStore(store, "alias", password, List.of("h3")), HttpConfig.defaults(), router);
```
Ví dụ: `Http3Example`. Kiểm chứng bằng client HTTP/3 của `aioquic` (12 kịch bản: GET/POST, 900 KB lên, 3 MB xuống, 60 request song song, 250 request tuần tự, 404/431/413/500, handler bất đồng bộ), unit test QPACK, và fuzz HTTP/3. *Chưa có*: streaming request/response, upgrade, server push, trailer ở response, RESET_STREAM cho lỗi mức stream (hiện trả 400), access log, header/body timeout riêng, client HTTP/3, quảng bá `Alt-Svc` từ server h1/h2. Đo trên k8s ở 0,5 CPU: khoảng 24 nghìn request/s (~19 µs CPU/request) với client aioquic từ ba pod, ngang HTTP/1.1 over TLS và thấp hơn nhiều so với h2 over TLS; chi tiết và giới hạn: `benchmark/RESULTS-K8S-H3.md`. So với h2 cùng một client Python trên mạng có trễ và mất gói (`benchmark/RESULTS-K8S-H3-VS-H2.md`): bắt tay nhanh hơn đúng 1 RTT, nhưng thông lượng thấp hơn h2, và khi mất gói 1% bản cài đặt này khôi phục chậm hơn TCP (khoảng một nửa thông lượng).

## Giới hạn đã biết
- Task của SSLEngine (xác thực chứng chỉ) chạy trực tiếp trên loop; TrustManager tuỳ chỉnh có chặn I/O sẽ làm đứng loop đó.
- `Context`/`Stage` chỉ gọi trên loop thread; từ thread khác dùng `connection.eventLoop().execute(...)`.
- HTTP: server và client có HTTP/1.1 và HTTP/2 (xem trên). Client chưa có pipelining, SOCKS, TLS tới proxy; server chưa nén response. Handler và continuation của future chạy trên loop nên không được chặn.
- MQTT: xác thực mở rộng (AUTH) chỉ được kiểm bằng peer giả và RFC 7677, chưa có broker thật nào để thử (Mosquitto không có sẵn phương thức nào); trạng thái phiên (tin QoS 1/2 chưa xác nhận, subscription) nằm trong bộ nhớ nên mất khi khởi động lại tiến trình; handler chạy trên event loop (không chặn); `publish` không chặn nên producer nên dùng `whenWritable()`. Client mới, ít được dùng thực tế hơn nhiều so với Paho.
- AMQP: callback consumer chạy trên event loop; một handler nặng hoặc chặn làm đứng mọi kết nối cùng loop (thư viện chính thức có pool thread riêng cho việc này), nên chuyển việc nặng sang executor rồi ack sau.
  `basicPublish` không chặn: producer phải dùng `isWritable()` / `whenWritable()` để không xếp dữ liệu vô hạn. Client mới, ít được dùng thực tế hơn nhiều so với `amqp-client`.
- Unix socket: file socket cũ do tiến trình bị crash để lại phải xoá thủ công trước khi bind lại.
